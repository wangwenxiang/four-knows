01 · Stripe 简述

从技术规模看，它是一家在极高可靠性约束下运行超大型金融软件系统的公司。

Stripe 于 2010 年由 Patrick 与 John Collison 兄弟创立。Patrick 是典型的少年技术极客： 8 岁在利默里克大学上第一门计算机课程、10 岁开始学习编程； 16 岁凭从零实现的 Lisp 方言 Croma（C 写的解释器 + 自研 VM + 用 Croma 自举的编译器， continuation 支持超越 Scheme），获得 2005 年爱尔兰第 41 届 Young Scientist of the Year 总冠军。 核心产品是一组面向开发者的支付、账单、税务、风控和资金基础设施 API。 2025 年平台总交易量为 1.9 万亿美元，折合日均约 52 亿美元。

Greg Brockman：Stripe 首任 CTO（2013 年起，公司从 5 人成长到 205 人）；2015 年 12 月与 Sam Altman、Ilya Sutskever 等共同创立 OpenAI，现任总裁。

Minions 是 Stripe 内部的无人值守、端到端编码 Agent 平台 （任务编排、隔离 Devbox、上下文注入、工具调用、质量门禁、CI 修复与 PR 生成）： 接收任务后，在隔离 Devbox 中自主理解代码、完成修改、执行门禁与 CI，并生成 PR； 目前每周合并超过 1,300 个完全由 Minions 编写、经人工 Review 的 PR。

03 · Minions 总体架构

模型只处理需要判断的节点；环境、门禁、Git、CI 和发布交给确定性系统。

Agent 判断 确定性平台 知识 / 工具 质量与审批
架构点 工程含义 公开资料映射
Blueprint（编排原语） “workflows defined in code”：一个状态机交错编排两类节点——确定性代码节点（Run configured linters、Push changes，完全不调 LLM）与 Agent 节点（Implement task、Fix CI failures）。支持逐节点上下文工程：限制该节点可用工具集、改写系统提示、简化对话历史。团队可自建 Blueprint，例如确定性 codemod 搞不定的 “tricky LLM-assisted migrations”。 Part 2 原文：“a state machine that intermixes deterministic code nodes and free-flowing agent nodes”；能预判的决策用确定性代码，“saves tokens (and CI costs) at scale”，“putting LLMs into contained boxes” 带来可复合的可靠性。
Devbox（执行环境） AWS EC2 实例，含全量源码与运行中服务；热池预置 10 秒内就绪——预克隆巨型 git 仓库、预热 Bazel 与类型检查缓存、常驻代码生成服务，就绪即在各主仓最近 master 上可跑 REPL / 测试 / 类型检查。每任务一台、用完即弃。跑在 QA 环境：无真实用户数据、无生产服务、无任意外网——因此可给 Agent 全权限、零确认弹窗，错误被限制在单 Devbox 爆炸半径内。 Part 2：就绪目标 “within 10 seconds”；无人值守环境三属性 “parallelizable, predictable, isolated”；不用本地容器 + git worktree 的原因是二者 “are hard to combine”。
Agent Harness 2024 年末内部 fork Block 开源代理 Goose，适配内部 LLM 基础设施；只针对无人值守场景开发（人监督场景直接给工程师用 Cursor / Claude Code）。系统提示极简——本质是 “implement this task completely, no mistakes”，复杂性全部放在工具与 Blueprint 编排层，而非 Prompt。 Part 1 / Part 2 确认 Goose fork 与时间点；ZenML 记录极简系统提示与 “directional breadcrumbs”（人先起头写 diff，Agent 接着做）技巧。所用具体模型两篇官方文章均未披露。
Toolshed（MCP 网关） 中心化内部 MCP Server，近 500 个工具（Part 1 时为 400+）：代码搜索（Sourcegraph）、内部文档、工单、构建状态、测试数据、SaaS API。一次注册、全 fleet（数百个 Agent 系统）即刻可用。关键取舍：默认只给 minion 一个刻意小的精选子集（“smaller box” 表现更好），可按主题成组添加；内部安全控制框架拦截破坏性调用。 Part 2 原文：“a centralized internal MCP server”、“nearly 500 MCP tools”、“an intentionally small subset of tools by default”。
Context Registry（规则文件） 规则即代码、三工具一份：标准化 Cursor 规则格式，harness 同时兼容遗留自研格式，并把 Cursor 规则同步为 Claude Code 可读——minion、Cursor、Claude Code 读同一套指导，避免重复维护。全局无条件规则“极为节制”，规则几乎全部按子目录 / 文件模式作用域化，文件系统遍历时自动附加。 Part 2 规则策略原文：“scoped to specific subdirectories or file patterns, automatically attached”；GitHub stripe-salesforce-ai-context 展示同构公开样本：LOAD_ALL.md、rules/*.mdc、244 个 v02_* 动作、2,175 模型 / 8,461 字段。
Verification Plane（验证面） 模型不能“口头通过”：push 时后台守护进程预计算 lint 启发式、修复不到 1 秒；300 万+ 测试做选择性执行（平均 5%、中位数 0.5%）；CI 失败先自动应用 autofix，无 autofix 的失败回灌 Agent 节点给一次本地修复机会；CI 硬上限 2 轮，之后必须交人工——理由是 CI “cost tokens, compute, and time”，无限循环边际收益递减。 Part 1 “at most two rounds of CI”；Part 2 lint “well under a second on a push”；Selective Test Execution 与 Sorbet 文章提供快反馈与类型门禁的实现（见第 07 节）。

04 · 强制工作流

Blueprint 的本质是：LLM 负责开放问题，程序负责可预知步骤。

Deterministic 预取上下文

解析工单、文档、构建链接，提前调用 MCP 注入。

Deterministic 分配 Devbox

干净分支、临时凭证、网络策略、资源预算。

Agent 实现任务

搜索、理解、编辑、运行局部测试；工具集受限。

Deterministic 本地门禁

format、lint、Sorbet、受影响测试、Secret 扫描。

Agent 修复诊断

只把实际失败输出交给模型，不接受口头“已通过”。

Deterministic CI ≤ 2 轮

先应用 autofix；第二轮后停止自动循环。

Approval PR + 人审

检查修改、验证记录、剩余风险，再决定合并。

节点 输入 系统动作 产物 / 停止条件
Context Prefetch
（预运行水合）		 Slack 线程及其中全部链接、工单、设计文档、构建链接。 在 minion 启动前，确定性地对 “likely-looking links” 执行对应 MCP 工具（Part 1 原文：hydrate context “before a minion run even starts”）：预取工单详情、内部文档、构建状态、Sourcegraph 代码情报。大型参考资料不全塞进模型，需要时按文件或符号补取。 可审计的 context snapshot；后续 Review 能看到 Agent 当时“知道了什么”。
Sandbox Provision
（热池签出）		 目标仓库、基线分支、任务权限、资源预算。 从热池签出 EC2 Devbox（10 秒内就绪）：巨型仓库已克隆到最近 master、Bazel 与类型检查缓存已预热、代码生成服务常驻；创建任务分支。QA 环境隔离即安全基线——无生产数据、无生产服务、无任意外网，因此可给全权限、零确认弹窗。 每任务一台隔离环境，可同时并行拉起多台；环境失败直接终止，不让 Agent 自行扩大权限。
Agent Work
（授权节点内自主循环）		 任务合同、上下文快照、本节点工具 manifest（刻意小的精选子集）、仓库规则。 Goose fork 在 Blueprint 授权的 Agent 节点内循环：搜索代码、编辑文件、跑局部测试。逐节点上下文工程：限制工具集、改写系统提示、简化对话历史。系统提示极简（“implement this task completely, no mistakes”）；运行全程有 “follow along” 链接可实时观察每步工具调用。 代码 diff、测试补充、运行轨迹；测试失败时 Agent 读取真实报错迭代（“reading error messages and adjusting code”），超预算则回到确定性节点。
Quality Gate
（本地门禁，shift left）		 代码 diff、变更文件、命令配置。 “Shifting feedback left”：会挂 CI 的检查必须在 push 前暴露。一个 linter 子集作为确定性 Blueprint 节点本地循环，直到能一次通过 CI 才 push；pre-push hook 自动修常见 lint 问题——后台守护进程预计算 lint 规则启发式并缓存，push 时修复耗时不到 1 秒；Sorbet 提供毫秒级类型反馈。 通过则 push 进 CI；失败把最小诊断片段交给 Agent 修复，不接受“我认为通过”。
CI Repair Loop
（硬上限 2 轮）		 CI 失败任务、日志、自动修复建议。 从 300 万+ 测试中选择性执行（平均约 5%、中位数 0.5%）；失败测试若有确定性 autofix 则自动应用；无 autofix 的失败送回 Agent 节点，给 “one more chance to fix the failing test locally”；第二轮 CI 后停止自动循环——CI “cost tokens, compute, and time”，无限循环边际收益递减。 可评审分支，或带失败证据的停止状态，由人类决定是否继续。
PR + 发起人闭环
（人审硬门槛）		 通过（或止步于）两轮 CI 的分支。 按 Stripe PR 模板生成 PR。发起工程师检查：满意则请求正式代码评审；不满意可给出进一步指令让 minion 推送更新；也可通过 SSH / VS Code 直接接管 Devbox 手工收尾。Agent 永不自主合并（“the agent doesn't merge code autonomously”）。 合并决策永远在人；不完美的运行 “often still an excellent starting point”。

05 · Context-as-Code

官方 GitHub 仓库不是 Minions 源码，但很好地展示了 Stripe 如何把领域知识、生成规则和可运行样例做成 Agent 可消费的代码资产。

stripe-salesforce-ai-context

核心价值不是“文档很多”，而是把 AI 容易幻觉的 API 面、元数据约束和部署规则写成可加载、可作用域化、可复用的工程文件。

context/ ├── LOAD_ALL.md # 加载索引 ├── Platform-Architecture.md # 架构与决策 ├── API-Extension.md # API 使用模式 ├── Stripe-Billing-Flows.md # 领域流程 ├── invocable-actions...md # 244 个 v02_* 动作 ├── models-reference.md # 2,175 模型 / 8,461 字段 └── rules/ ├── flow-builder.mdc # globs: **/*.flow-meta.xml └── lwc-stripe-payment.mdc # globs: **/*.{js,html,cls} examples/force-app/ # Flow / Apex / LWC 可部署样例 setup/ # Scratch Org prompts/ # 加载入口

上下文分层

LOAD_ALL.md 是单一加载入口：核心上下文约 35K Token 先加载；两个大型引用文件约 195K Token 明示 “Do not load them upfront”，且必须成对按需加载（“Always load both together” —— action 名与模型字段总是配套使用）。

核心架构 Universal Connector、API Extension、Billing Flow 的关系与选型 ~35K Token
作用域规则 .mdc 使用 glob 生效，alwaysApply: false，避免规则全局污染 Scoped
大型字典 actions-reference ~33K（244 个 v02_* 动作）+ models-reference ~160K（2,175 模型 / 8,461 字段），成对加载 On demand
Golden Examples Flow XML、Apex helper、LWC Payment Element 组成可部署样例 Executable
动态工具 Salesforce CLI / MCP / Stripe MCP 查询真实 Org 和 API 状态 Runtime

规则必须具体

  • Flow 除 start 外每个元素必须有入边
  • Trace connector / faultConnector / scheduledPaths
  • 骨架固定 apiVersion 64.0、AUTO_LAYOUT_CANVAS、locationX/Y=0
  • 每个 callout 五项强制参数：accountRecordId、idempotencyKey（模式 {!$Flow.InterviewGuid}-{Operation}-{RecordId}）、ignoreBillingSyncEventProcessing、performDmlSaveAfterCalls、faultConnector
  • 生成状态保持 Draft，部署后人工激活；生成后回溯每个 connector 目标验证连通性

领域约束进入代码

  • Callout 使用 AsyncAfterCommit
  • 每次 Stripe API 调用先解析 Stripe_Account__c
  • LWC 用 data-stripe-element 属性挂载（Shadow DOM 会把 ID 重写为 payment-element-86）
  • 3DS 用服务端确认（LWS 禁止 confirmPayment() 注入模态框）+ 纯 JS 重定向；支付状态只由 webhook 回写
  • webhook 异步延迟用 Queueable 重试：最多 3 次、每次延迟 1 分钟，先同步查一次快路径

知识必须能验证

  • 静态规则可由 lint / 编译检查
  • Golden Example 可部署到 Scratch Org / Sandbox
  • CSP Trusted Sites 必须 Setup UI 手工配全 6 个指令——frame-src 缺失时 Payment Element 渲染为空容器且 UI 无报错
  • SOQL 使用 WITH USER_MODE，DML 需显式 CRUD/FLS
  • 规则和 API 版本随代码评审一起演进
GitHub 文件 / 代码规则 可提炼的平台能力 对 Minions / 企业 Agent 平台的启示
LOAD_ALL.md + README 索引 + 分层预算：核心 ~35K 常驻，引用 ~195K 按需成对加载；README 的推荐启动语只有一句——“Read context/LOAD_ALL.md and load the core context files it lists. When ready, tell me what you loaded.”（加载 + 自检确认模式）。 平台应记录每次任务的 context snapshot：加载了哪些文件、哪些版本、哪些规则命中，方便 Review 和回放。
flow-builder.mdc frontmatter 三字段（description / globs / alwaysApply: false）把规则作用域绑定到 **/*.flow-meta.xml；规则主体是可机检的结构不变量：除 start 外每元素必须有入边、五项强制 callout 参数、AsyncAfterCommit、生成后逐 connector 验证——每条都配 WRONG/RIGHT 对照与报错原文（如 “apexClass is invalid”）。 Agent 写低代码 XML 时，最关键的不是自然语言说明，而是可机检的结构不变量和部署前门禁。
API-Extension.md 三分支决策树：v02_* 强类型动作覆盖 “95%+ of use cases”；未覆盖端点 / beta / 指定 API 版本走 AgnosticInvocable（原始 endpoint + URL-encoded form body，非 JSON）；跨 Flow 复用或深嵌套构造封装 Helper Invocable。文末给 AI 的六步指引：先搜 actions-reference → 再搜 models-reference → 优先强类型 → 永远设 accountRecordId。 工具选择应是决策树：强类型动作优先，通用 API 调用兜底，重复模式沉淀为内部平台能力。
lwc-stripe-payment.mdc 规则覆盖 CSP 6 指令（frame-src 为关键坑）、Stripe.js 必须 CDN 加载（PCI 要求）、renderedCallback 是唯一安全挂载点（配 guard flag）、服务端确认三步流程、webhook 状态机（metadata 带回 SF 记录 ID、解析 Request_Body__c 原始 JSON）、Queueable 3×1min 重试，以及 14 条 Common Mistakes 清单。 前端 Agent 需要同时理解浏览器安全、支付合规、Salesforce 生命周期和后端一致性，不能只生成 UI 代码。
README + Platform-Architecture.md 的 agent 元指令 直接写给 Agent 的操作规程：docs.stripe.com 任意子页加 .md 后缀可得干净 markdown；“Do not guess API parameters”；“Never assume an action doesn't exist — always search the reference files first”；无 org 访问时用占位字段名并写入激活前清单；CLI 统一用 sf（弃 sfdx）。 上下文资产里应包含“Agent 行为规范”层：怎么查文档、什么禁止臆测、拿不到运行时信息时的降级动作——这与代码规则同等重要。
prompts/ + examples/ 验证闭环 load-stripe-context.txt 是无文件访问工具（ChatGPT 等）的降级方案：列 8 个待读文件 + 固定确认文案 + 6 条 KEY RULES。examples 全部标注 “Status: Validated”，五步流水线：Context loaded → Prompted → Generated → Validated（部署到 scratch org 端到端验证）→ Published；README Troubleshooting 表把每个常见故障映射回对应规则。 Golden Example 必须真的部署验证过才能入库；故障与规则双向索引，让规则库随失败案例持续演进——这就是可运维的知识库，而非静态文档。

06 · 面向 2,000+ 仓库的复制方式

中央建设平台，业务部门维护领域 Context；不能按部门复制二十套 Agent 基建。

仓库准入条件： 必须有稳定的 bootstrap、format、lint、typecheck、test-changed、security-scan 命令，以及架构说明、Code Owners 和可计算验收标准。 没有这些基础的仓库，应先治理，再开放无人值守写代码。
治理层 平台团队负责 业务仓库负责 上线判据
运行时 Runner 镜像、Devbox 预热池、任务级凭证、网络策略、资源预算、run trace。 声明 bootstrap / test / build 命令，维护本仓缓存策略和代码生成入口。 新任务可在干净环境内一键恢复，失败可通过日志定位到命令或权限。
上下文 Context Registry、版本索引、加载快照、全局安全规则、跨仓通用规则。 维护架构说明、目录级 .mdc、API 字典、Golden Examples、领域术语表。 Agent 能在不问人的情况下找到正确 API、正确入口和正确测试。
工具 MCP Gateway、工具注册、权限边界、审计日志、敏感操作审批策略。 提供领域只读查询、沙箱写操作、Mock / fixture / 测试数据生成工具。 工具返回结构化结果；敏感工具有最小权限和可追踪调用记录。
评估 Golden Task 评测平台、回归集、成本/成功率/人工干预率报表。 提交真实历史任务、失败样本、代码评审规则和业务验收脚本。 在代表性任务集上通过率、误改率、CI 成本和 Review 负担达标。

从 0 到 1 的建设顺序（由溯源事实推导的最小可行路径）

Stripe 的每一层都先于 Minions、为人类工程师而建（“what's good for humans is good for agents”）。复刻时按同样顺序，每层有明确验收，再叠下一层。

0 · 仓库治理 bootstrap / format / lint / typecheck / test-changed / security-scan 全部命令化且快而确定——这是 Agent 反馈回路的原料，没有它后面全部失效 验收：干净机器一键跑通
1 · 隔离执行环境 每任务一台、热池预置（Stripe 基准：10 秒就绪，预克隆仓库 + 预热构建/类型缓存）；隔离到无生产数据、无任意外网——用隔离边界换取 Agent 全权限、零确认弹窗 验收：并行 N 台互不影响
2 · Harness + 工具网关 fork 或选用开源 harness（Stripe 于 2024 末 fork Block Goose；今天可选 Goose / Claude Agent SDK），接统一 MCP 网关（Toolshed 模式：一次注册全 fleet 可用），默认工具集刻意小 验收：一个任务端到端跑完
3 · Context-as-Code 规则文件与人类 IDE 工具共用同一份（Cursor 格式 + 自动同步）、按 glob 作用域化；LOAD_ALL 式索引 + 分层 token 预算 + 大字典按需成对加载 验收：Agent 不问人能找对 API
4 · Blueprint 编排 状态机把 Agent 节点关进确定性节点之间：lint 本地循环到能一次过 CI 才 push；CI 失败先 autofix、无 autofix 给 Agent 一次机会、硬上限 2 轮 验收：无人值守跑完并出 PR
5 · 入口、观测与度量 Slack @App / CLI / Web 多入口 + 自动派单（flaky test 一键修复模式）；follow-along 实时轨迹;度量 PR/周、合并率、人工干预率、每 PR token 与 CI 成本 验收：非工程角色也能派单

07 · 支撑子系统实现细节

Minions 验证面的两块地基：分钟级选择性 CI 与毫秒级类型反馈。复刻 Minions 之前，先复刻反馈回路。

Selective Test Execution：动态观测，不做静态分析

Ruby 的元编程、动态分派与非 Ruby 输入（YAML / fixture / 模板）使静态依赖分析不可靠。核心思路：“instead of guessing what a test might touch, we record what it did touch” —— 不猜测试会碰什么，记录它实际碰了什么。两种失败模式被显式命名：Underselection（漏选，危险）与 Overselection（多选，拖慢）。

采集 file_access_interceptor（自研 C++ 共享库，LD_PRELOAD 注入） ├─ 为每个运行中的测试设置层级 scope（// 分隔，根为 r） ├─ 拦截 open() 及变体，把被打开文件映射到当前 scope ├─ 热路径极简：仅向每进程文件追加一条记录 └─ LD_PRELOAD 自动传播到子进程 聚合 worker → build scheduler（sidecar 进程）→ 倒排 └─ 选择索引：roaring bitmap（文件 → 受影响测试），约 30 亿数据点 选择 file inventory（hashdeep 并行哈希，覆盖 Git 外生成产物） → 与 STE base 基线做哈希 diff → 变更文件 → 位图并集 → 护栏 └─ 基线定位：MRI 单调修订号（祖先关系 ⇒ MRI 单调递增）， 一次 DB 查询（MongoDB）取最新完整数据集，确定且可复现 护栏 此前失败的测试永远重跑；glob 发现型测试标记 mandatory 永远执行； 根 scope 文件变更 ⇒ 触发全量；linter（RuboCop 等）同样按变更选择

效果：平均一次构建只跑测试套件的 5%、中位数 0.5%，算力不到“全跑”策略的 10%；每周约 5 万次构建支撑 “a few minutes, not four months”。

Sorbet：让 5,000 万行 Ruby 拥有可机检的类型门禁

C++ 实现的 Ruby 渐进类型检查器（可编译为 WebAssembly）。覆盖超过 1,500 万行、15 万个文件；80% 的编辑在毫秒级返回类型错误。速度来自设计：只做方法内局部类型推断——检查是“方法内代码 + 不可变索引”的纯函数，天然并行（embarrassingly parallel）。

# 文件级 sigil 渐进收紧 # typed: true 未签名方法参数按 T.untyped（best-effort） # typed: strict 停止假设 T.untyped，所有方法必须有 sig sig {params(invoice: Invoice, paid: T::Boolean).void} def update_invoice(invoice, paid); end update_invoice('in_1KZ7…', true) # error: Expected `Invoice` but found `String` # for argument `invoice`
起源 2016-11 先有仅运行时的 declare_method 注解；2017-11 从零自研 Sorbet；2018-05 成为 CI 必过项；2019-06 开源 Timeline
推广机制 CI 在每个 PR 上发布 “Stripe code quality score” 评论（加权和，包含低于 strict 的非测试文件数） Culture-as-CI
现状 85% 非测试文件为 typed: strict；超过 95% 的全部文件为 typed: true；NameError 类生产事故被静态类型错误整体取代 Adoption
对 Agent 平台的意义：这两个子系统先于 Minions 存在、为人类工程师而建，却构成了 Agent 验证面的全部地基——Agent 每次修改都能在分钟级拿到高置信反馈，“最多两轮 CI”的预算才成立。这正是 “what's good for humans is good for agents” 的具体形态：想复刻 1,300 PR/周，先把 bootstrap / lint / typecheck / test-changed 做成快而确定的命令。
