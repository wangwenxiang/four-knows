Self-improving Agent 真的会越用越强吗？ Salesforce AI Research 这篇论文给这个问题降了一点温。 作者重新评估了两种 Memory-based 自进化方法，发现加入自我改进循环后，Agent 的表现反而更不稳定。 在 71% 的实验中，不同运行之间的方差变大。同一套配置，最好和最差的一次结果甚至能相差 10 个百分点。 更关键的是「任务顺序」。 很多 benchmark 默认把任务按固定顺序运行，无意中形成了一个从简单到困难的课程。沿着这个顺序，ReasoningBank 平均提升 1.5%；把任务随机打乱后，表现反而下降 4.5%。 作者进一步检查 Memory，发现 Agent 很容易从模糊任务里总结出「看起来合理、实际不可用」的经验。 比如环境只能操作浏览器，它却把「调用 API」写进长期记忆；一旦这种错误经验被反复检索，还可能继续影响后面的任务。 这也提醒我们看到一次 evolution 后分数上涨，还不能急着说 Agent 学会了。 至少要多跑几次、打乱任务顺序，也要检查它到底把什么东西写进了长期记忆。 真正可靠的自进化，需要经得起随机性和任务顺序的扰动。 📎 arxiv: https://t.co/dCBCxLXhNO

The latest RAG trend for the current agent harnesses (Codex, Cowork) is to do two passes of document processing to solve a knowledge work task over a data room of documents: 1️⃣ A fast and light pass, oftentimes using a free/OSS doc parsing tool. This can be cheaply run across 10-100-1k’s of files, and enables the agent to then do retrieval (e.g. grep, semantic) to find relevant subsets of context. 2️⃣ A “just-in-time” VLM-based pass. Once the agent finds the relevant pages of context, it will screenshot the documents can call its own VLM (or write code) to dissect the pages. The issue with only using VLM-based OCR tools over massive ad-hoc customer file dumps is that it’s slow and expensive. Doing JIT VLM OCR allows the agent to filter through the data cheaply, but still preserve accuracy for the context that’s needed for the task. The agent harnesses do two-pass document processing by default using off the shelf-tools: pdf2text as the first pass, and using itself (Opus 5) as the second pass. See the below video where Cowork runs over a bunch of PDFs to answer a question about a benchmark graph in the Kimi k3 paper. The main issues here with the “out of the box” doc processing these agents offer are: * Opus 5 is not the best VLM for OCR. It is also way too expensive at scale and lacks grounding * The OSS tools like pypdf, pdf2text, may not be versatile enough as the first pass. * The agent will write a lot of throwaway code to rewrite things an OCR tool would’ve provided out of the box, like chart processing, bounding boxes, confidence scores, leading to increased cost and speed. We have all the tools within @llama_index to help any agent do two-pass document processing with higher accuracy and lower cost. 1️⃣ We have liteparse for the first pass - a free/OSS parser written in Rust that’s faster/more accurate than other OSS parsers, and supports 50+ document types 2️⃣ We have LlamaParse for the second pass - an agentic document engine that uses VLMs+harnesses to achieve SOTA in accuracy and cost across various doc parsing and extraction tasks. It can be called from any agent harness as an MCP or skill. It takes in page numbers as input, so that the agent can choose to run LlamaParse over a subset of the doc instead of the full doc as a “zoom-in” pass. Come check it out! LiteParse: https://t.co/JNER0mVcB8 LlamaParse: https://t.co/XYZmx5TFz8 All the relevant docs, including MCP, are here: https://t.co/qc9Q5NT3Jr

当前 agent harness（Codex、Cowork）里最新的 RAG 趋势，是对数据室中的文档进行两轮处理，以完成知识工作任务： 1️⃣ 快速轻量的一轮，通常使用免费的/OSS 文档解析工具。它可以低成本地跑过 10、100 乃至上千个文件，让 agent 随后通过检索（如 grep、语义检索）找到相关上下文子集。 2️⃣ 基于 VLM 的“即时”处理。当 agent 找到相关页面后，会对文档截图，并调用自己的 VLM（或编写代码）来解析这些页面。 如果只对海量临时客户文件包使用基于 VLM 的 OCR 工具，问题在于速度慢且成本高。JIT VLM OCR 让 agent 能低成本筛选数据，同时仍能为任务所需上下文保留准确性。 这些 agent harness 默认使用现成工具进行两轮文档处理：第一轮用 pdf2text，第二轮用自身（Opus 5）。下面的视频展示了 Cowork 如何遍历一批 PDF，回答关于 Kimi k3 论文中某个基准图表的问题。 这些 agent 提供的“开箱即用”文档处理主要问题是： * Opus 5 并不是最适合 OCR 的 VLM。它在规模化使用时也过于昂贵，并且缺少 grounding * pypdf、pdf2text 等 OSS 工具作为第一轮处理可能不够通用 * agent 会写大量一次性代码，去重写 OCR 工具本可开箱提供的能力，比如图表处理、边界框、置信度分数等，从而增加成本并拖慢速度 我们在 @llama_index 中已经有完整工具，能帮助任何 agent 以更高准确率、更低成本进行两轮文档处理。 1️⃣ 第一轮有 liteparse，这是一个用 Rust 编写的免费/OSS 解析器，比其他 OSS 解析器更快、更准确，并支持 50 多种文档类型 2️⃣ 第二轮有 LlamaParse，这是一个 agentic 文档引擎，使用 VLM+harness 在各种文档解析和抽取任务中实现 SOTA 的准确率和成本表现。它可以作为 MCP 或 skill 被任何 agent harness 调用。它接受页码作为输入，因此 agent 可以选择只在文档子集上运行 LlamaParse，而不是对整篇文档运行，相当于一次“放大查看”处理。 欢迎来看看！ LiteParse：https://t.co/JNER0mVcB8 LlamaParse：https://t.co/XYZmx5TFz8 包括 MCP 在内的所有相关文档都在这里：https://t.co/qc9Q5NT3Jr

we've been iterating a lot on how DocWriter internally represents a user's writing style! the naive approach is to dump all a user's prior writing in context and pray the AI figures out how to sound like them. this doesn't really work. and the user can't just manually specify their style either, because nobody knows what their meaningful writing preferences (for an AI agent) actually are. so we've built a multi-agent pipeline that runs lexical, grammatical, and discourse analyses on the user's writing, extracts specific patterns with evidence, and then surfaces them in a UI where the user can confirm or reject each pattern by comparing two passages side by side TBD on how well it performs in our next round of user studies 😆 it feels like we are really trying to do anything possible to avoid fine-tuning, but perhaps we need to bite the bullet eventually

我们一直在反复迭代 DocWriter 内部表示用户写作风格的方式！ 最朴素的做法是把用户过去所有写作都塞进上下文，然后祈祷 AI 能自己琢磨出怎么写得像他们。但这其实行不通。用户也不能手动指定自己的风格，因为没人真正知道自己对 AI agent 来说有意义的写作偏好到底是什么。 所以我们构建了一条多智能体流水线，对用户写作进行词汇、语法和篇章分析，提取带证据的具体模式，然后在 UI 中展示给用户，让他们通过并排比较两段文字来确认或拒绝每个模式。 下一轮用户研究中表现如何还有待观察 😆 感觉我们真的在竭尽所能避免微调，但也许最终还是得硬着头皮上
