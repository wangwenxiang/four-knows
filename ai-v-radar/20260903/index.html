I want to prevent a race into unmonitorability kicked off by confused reporting. The depth of the computation graph for our present frontier models, including Astra, is within a factor of two of GPT-4. OpenAI has worked to preserve and utilize chain-of-thought monitoring since our very first reasoning models. I do think it is fragile and unfortunately trending in a negative direction, for reasons not contingent on architecture changes that I will write about soon. But there are things we can do to strengthen it, and it's a core goal of our current research program.

很多高风险 Agent 的流程里，都有这样一个设计： 最后让人点一下「确认」。 听起来很稳妥，但问题是，当一个 Agent 已经连续跑了几十步、调用了很多工具之后，那个负责确认的人，真的还知道前面发生了什么吗？ Hugging Face 的 Margaret Mitchell 等人这篇论文，讨论的就是这个问题。 我们一直习惯把 Human-in-the-loop 当成安全兜底，但长时 Agent 会不断消耗人的注意力。用户需要跟踪计划、工具调用、状态变化，还要持续做审批。 时间一长，很容易出现 approval fatigue：按钮还在点，注意力已经跟不上了。 更麻烦的是，长期依赖自动化还可能削弱人的领域判断和接管能力。 于是，一个很现实的问题出现了： 真正需要人介入的时候，这个人可能已经离任务太远。 论文建议把人的认知状态也纳入 Agent 系统设计。比如在关键节点主动恢复上下文、减少无意义审批，同时通过训练、轮换和休息，让监督者保持真正的判断能力。 这篇给我们的一个很直接的提醒是： Human-in-the-loop 的重点，从来不只是「流程里有没有一个人」。 更关键的是，那个人到关键时刻，还能不能理解、判断和接管。 📎 arxiv: https://t.co/HneMWkoNxk

Most teams can tell you what their agent does. Very few can tell you what it is allowed to do. Different questions. The second is the expensive one. Agent integrations usually run through a service account, and that account tends to hold generous permissions, because narrowing them is fiddly and everything works fine while they are wide. So the agent can reach far more than the task needs. Nobody decided that. It arrived by default. Role-based access control is a must for this. Scope the agent to whoever triggered it, resolved at runtime, not a static account holding keys to everything. Second reason, nothing to do with security: hand a model too many available actions and it gets worse at choosing between them. You burn context on options it never uses. A narrow scope is not only safer. It performs better. So what should you ask your team this week? Not what your agents do. What they could do today, if one of them decided to.

大多数团队都能告诉你他们的 agent 会做什么。 很少有团队能告诉你它被允许做什么。 这是两个不同的问题。第二个才是代价高昂的问题。 agent 集成通常通过服务账号运行，而这个账号往往拥有很宽泛的权限，因为收窄权限很麻烦，而且权限放宽时一切都能正常工作。 于是 agent 能访问远超任务所需的范围。 这不是谁刻意决定的，而是默认状态自然形成的。 基于角色的访问控制对此是必需的。应当在运行时把 agent 的权限限定到触发它的那个人，而不是用一个静态账号掌握所有权限。 第二个原因和安全无关：给模型太多可用动作，它在选择时反而会变差。你会把上下文浪费在它永远不会用到的选项上。更窄的范围不只是更安全，性能也更好。 所以这周你应该问团队什么？ 不是你的 agent 会做什么，而是如果其中一个今天决定行动，它能做什么。
