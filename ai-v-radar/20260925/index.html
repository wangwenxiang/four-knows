好的 Harness，不该永远绑死在模型外面。 更理想的状态，是它先教会模型怎么做事，然后自己退出。 北大等团队这篇 Harness-Zero，研究的就是「Harness 蒸馏」。 现在很多 Agent 的能力，其实来自外部 Harness：工具、Memory、Skill、执行规则……一旦换环境，或者把 Harness 拿掉，能力也容易跟着掉。 Harness-Zero 的做法比较有意思： 先优化出一套专用 Harness，再让 Harnessing Agent 用它去检查 Student 的每一步行动。 Student 做对了就放行，做错了就做最小修改。最后把这些被纠正后的完整轨迹，通过 SFT 蒸馏回模型参数里。 部署时，专用 Harness 和 Harnessing Agent 都可以拿掉，只保留一个轻量基础 Harness。 结果是在基础模型平均成功率 23.3%，挂上专用 Harness 是 41.7%，蒸馏后拿掉专用 Harness还能达到 44.3%。 论文还检查了 28 种原本只有 Harness 才会触发的行为，模型最终平均学回了 82.3%。 所以这样看来 Harness 可能不只是运行时基础设施，也可以是训练阶段的「行为教师」。 先把好的工作方式探索出来，再慢慢压回模型本身。 📎 arxiv: https://t.co/ryAfLfEA67

Before an agent answers a single support ticket, someone has to sit down and write. That writing is the real project. The model can already read a message, tag it, draft a reply and flag the messy ones. What it cannot guess is where your team draws the lines. Which messages count as routine. When a complaint is about quality. How unsure is too unsure. Someone has to write out what done looks like for that one job, clearly enough to run unsupervised. Then it knows that job. Ask it to also flag who is about to churn and it cannot. One job, one written definition of done. Then the next.

在智能体回答任何一张支持工单之前，必须有人坐下来写清楚规则。 这份写作才是真正的项目。 模型已经可以读取消息、打标签、起草回复，并标出棘手问题。 但它无法猜出你们团队的边界在哪里。哪些消息算常规问题。什么时候投诉属于质量问题。不确定到什么程度就算太不确定。 必须有人把这一项工作的“完成”标准写出来，清楚到足以让它无人监督地运行。 然后它就懂了这项工作。让它顺便标出谁快要流失，它做不到。 一项工作，一份写清楚的完成定义。然后再做下一项。
