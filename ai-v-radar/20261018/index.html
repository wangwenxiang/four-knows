Claude Code 团队称，现在大约 90% 的代码已经由 Claude 写。那这么多代码到底谁来 Review？ Anthropic 最新这篇文章给了一个很这得参考的答案。 他们已经把 Code Review 从 PR 最后的人工关卡，拆成了一条持续验证链。 代码提交前，Agent 自己跑测试，再开一个干净 Context 的 Subagent 看 diff；PR 创建后自动跑 Claude Review 和 Security Review；人主要盯风险、架构和改动意图；合并后还有 Feature Flag、灰度和快速回滚。 按 Anthropic 的内部数据，6 月到 9 月合并的 PR 数量翻了一倍多，回滚率反而下降超过 40%。研究版 AI Review 上线后，有实质性 Review 意见的 PR 也从 16% 提到了 54%。 这里真正值得看的，是 AI Coding 把代码生产速度拉高以后，Code Review 也开始被重新设计。 人以后肯定越少逐行看 diff，把注意力留给意图、系统影响和那些机器很难替你承担的判断。 甚至每次漏掉一个 Bug，都可以继续写回 CLAUDE.md、REVIEW.md 或新的自动检查里，让下一次 Review 更强。 代码可以越写越快，真正要跟着一起扩容的是验证系统。 文章 https://t.co/3NHUxOMQRV

终于解读到一篇关于 FDE 的论文了，对 FDE 感兴趣的可以看看。 相比平时从岗位、公司案例去理解 FDE，这篇《FDE-Gym》更像是在用一套系统评测，研究 AI 到底能不能承担 Forward Deployed Engineer 这类真实企业交付工作。 作者把真实企业项目改造成 95 个任务，覆盖金融、医疗、制造、能源等 18 个行业。 Agent 拿到的通常只有客户最初的一句话需求。它需要自己读文档、查系统、找人确认信息，还要判断客户真正的问题到底是什么。 评分也很有趣： 完成需求本身还不够，最终交付的系统必须真正改善业务指标；乱找人、反复试错和等待都会产生额外成本。 结果是最强模型平均得分只有 0.56，95 个任务里真正解决的只有 14 个。 最大的瓶颈，往往是那些没有写进需求里的业务规则、隐性约束，以及客户自己都没表达清楚的问题。 其实对于 FDE 这个角色，真正难的地方一直都不只是「把东西做出来」。 更难的是在信息不完整、需求模糊、组织复杂的环境里，先判断到底该解决什么，再把结果真正交付出去。 📎 arxiv: https://t.co/eRRRkafPsW

Some observations about the "total" automation of software engineering: 1. There are more software engineers now than in 2025, and demand is growing. 2. Software engineers have never worked harder than they do now. 3. They largely don't write code anymore, agents write ~100% of the code. 4. The bottom line of the companies that employs these engineers and agents (i.e. the terminal purpose of all this code) is typically not budging as a result of AI adoption. This is why you have to think in terms of systems. Automating one aspect of a system creates its own friction and moves the bottlenecks elsewhere.

关于软件工程“全面”自动化的一些观察： 1. 现在的软件工程师比 2025 年更多，而且需求还在增长。 2. 软件工程师从未像现在这样忙碌。 3. 他们基本不再亲自写代码，智能体编写了近乎 100% 的代码。 4. 雇用这些工程师和智能体的公司，其利润（也就是编写所有这些代码的最终目的）通常并未因采用 AI 而有所改善。 这就是为什么必须从系统角度思考。将系统中的某个环节自动化，会产生新的摩擦，并将瓶颈转移到其他地方。
